# Критерии оценки репозиториев

Repo Radar оценивает не абстрактное качество проекта, а его практическую пригодность для внедрения, R&D или дальнейшего наблюдения.

## Критерии

Каждый критерий можно оценивать по шкале 1–5.

| Критерий | Что оценивается |
|---|---|
| Функциональность | Насколько проект реально решает заявленную задачу |
| Зрелость | Стабильность, история разработки, качество релизного процесса |
| Активность | Частота обновлений, issue/PR activity, состояние проекта |
| Лицензия | Возможность использования, модификации и коммерческого применения |
| Self-hosting | Возможность автономного размещения и контроля данных |
| Безопасность | Модель авторизации, работа с секретами, сетевой периметр, опасные default-настройки |
| Документация | Качество README, installation guide, architecture docs и troubleshooting |
| API и интеграции | REST/API, MCP, webhooks, GitHub/GitLab, CLI и другие интерфейсы |
| Сложность внедрения | Зависимости, требования к ОС/железу, эксплуатационная нагрузка |
| Практическая ценность | Насколько проект полезен именно в рассматриваемых сценариях |

## Итоговая оценка

Итоговая оценка в карточке проекта приводится по шкале 1–10 и не обязана быть простым средним арифметическим. Проект может быть технически сильным, но получить более низкую итоговую оценку из-за лицензии, несовместимости, сложности эксплуатации или отсутствия практического сценария.

Оценка и статус — разные вещи. Оценка характеризует общую привлекательность проекта, а статус показывает, какое действие с ним имеет смысл делать сейчас.

## Канонические статусы

В карточках и корневом каталоге используется только один из шести статусов:

| Статус | Когда использовать |
|---|---|
| **Изучить** | Проект потенциально полезен, но для установки или внедрения пока недостаточно информации |
| **К практическому тесту** | Проект достаточно понятен, чтобы проверить его на реальной задаче |
| **R&D** | Технология перспективна, но слишком молода, экспериментальна или зависит от нестабильного стека |
| **Использовать** | Есть достаточно оснований применять проект в рассматриваемом сценарии |
| **Следить** | Сейчас внедрение нецелесообразно, но проект стоит периодически перепроверять |
| **Отказаться** | Выявленные ограничения делают проект непригодным для рассматриваемого сценария |

Фразы вроде «проверить первым», «развернуть и проверить», «автоматизировать» или «использовать как reference» относятся к рекомендации внутри раздела **Решение**, но не являются отдельными статусами.

Типичный путь проекта:

`Изучить` → `К практическому тесту` / `R&D` → `Использовать` или `Следить` / `Отказаться`.

## Обязательные проверки перед внедрением

Перед реальным внедрением следует повторно проверить:

- текущую версию и дату последнего релиза;
- активность upstream;
- лицензию;
- security advisories и открытые критические issues;
- актуальные требования к ОС, runtime, GPU/CPU и памяти;
- состояние API и интеграций;
- способ обновления и отката;
- резервное копирование данных;
- требования к внешнему сетевому доступу.
