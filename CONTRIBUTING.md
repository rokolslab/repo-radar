# Contributing to Repo Radar

Спасибо за интерес к Repo Radar. Репозиторий задуман как практический каталог GitHub-проектов, поэтому главное требование к любому изменению — добавлять полезную оценку, а не копировать upstream README.

## Предложить репозиторий

Для предложения нового проекта используйте GitHub Issue с шаблоном **Repository suggestion**.

Желательно указать:

- ссылку на GitHub-репозиторий;
- зачем он заслуживает рассмотрения;
- предполагаемую категорию;
- конкретный сценарий использования, если он уже понятен.

## Добавить полноценную карточку

1. Выберите одну основную категорию из `docs/categories.md`.
2. Создайте каталог `repos/<category>/<repo-name>/`.
3. Создайте `README.md` по шаблону `templates/repository-review.md`.
4. Добавьте проект в таблицу соответствующей категории в корневом `README.md`.
5. Если нужна новая категория, сначала добавьте её описание в `docs/categories.md`.

Один проект хранится только в одной основной категории. Пересекающиеся свойства фиксируются внутри карточки.

## Что должно быть в обзоре

Карточка должна по возможности отвечать на следующие вопросы:

- что это за проект;
- какую проблему он решает;
- как устроен технически;
- как его установить или развернуть;
- какие API и интеграции доступны;
- где его можно использовать практически;
- какие есть сильные стороны;
- какие ограничения и риски обнаружены;
- с чем он пересекается в Repo Radar;
- какой практический тест имеет смысл провести;
- каково итоговое решение по проекту.

## Правила качества

- Не копируйте большие фрагменты upstream README.
- Отделяйте факты из документации проекта от собственной оценки.
- Для быстро меняющихся данных указывайте, что это состояние на момент анализа.
- Не выдавайте количество stars, версию, требования или совместимость за вечные свойства проекта.
- Проверяйте лицензию и не переносите в Repo Radar чужой код без необходимости.
- Для installer-команд, shell scripts и security-sensitive конфигураций явно отмечайте необходимость проверки перед запуском.
- Оценка должна отражать практическую полезность, а не популярность проекта.

## Оценка

Используйте критерии из `docs/evaluation-criteria.md`. Итоговая оценка не обязана быть математическим средним: это сводное решение, которое должно быть объяснимо содержанием карточки.

## Pull Request

Один PR желательно посвящать одному репозиторию или одной связанной группе изменений. Перед отправкой проверьте:

- ссылки внутри Markdown;
- соответствие структуры каталога;
- отсутствие дублирующих категорий;
- отсутствие секретов, токенов, приватных адресов и персональных данных;
- корректность названия upstream-репозитория и ссылки на него.

Спасибо за вклад.
